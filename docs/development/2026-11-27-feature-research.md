日期：2026-11-27  
适用范围：`zy-player-web`（Web / GitHub Pages / Python 网关 / Android App）

## 任务 9：跳过片头 / 片尾可行性调研

### 1. 业务背景
当前播放器已支持「快进 30s / 1m」、拖动进度条、续播记忆及全屏选集，但连续观看电视剧/动漫时，每集仍需手动跳过固定长度的片头曲与片尾曲。

### 2. 可选技术方案对比

| 方案 | 核心思路 | 准确率 | 开发成本 | 运维/存储成本 |
|---|---|---|---|---|
| **方案 A：手动快捷跳过 + 单剧用户记忆（推荐一期）** | 在播放器内提供「设置本剧片头/片尾时长」或「记为片头结束点」按钮；按 `vodKey` 记忆 `intro_sec` / `outro_sec` 并随 `/api/sync` 云端同步。新集开播时自动从 `intro_sec` 起播，距片尾仅剩 `outro_sec` 时浮现「跳过片尾（进入下一集）」按钮或倒计时自动切集。 | 100%（由用户指定） | **低（1~1.5 人日）** | 极低（每部剧仅多 2 个整数） |
| **方案 B：剧集公共时间段库（众包/后台配置）** | 后台建立 `vod_skip_markers(title_key, intro_sec, outro_sec, votes)` 表，结合运营配置或高置信用户上报投票下发默认起止点，用户个人设置可覆盖。 | 高（热门剧准确） | **中（2~3 人日）** | 低（SQLite 单表） |
| **方案 C：音视频指纹 / 黑屏静音帧自动识别** | 服务端拉取相邻两集前 3 分钟、后 4 分钟切片，使用 `ffmpeg` + Chromaprint / 帧哈希比对公共片段，自动计算片头片尾区间。 | 中高（受片源广告、变调影响） | **高（5~8 人日）** | **高**：平板 Termux CPU/内存与流量开销大，易拖慢播放且存在外部 CDN 防盗链失败 |

### 3. 推荐落地路线
1. **第一阶段（高性价比，立即可做）**：采用 **方案 A（单剧用户记忆 + 快捷设置）**。
   - 数据结构：在 `progress` 或新增 `skip_cfg[vodKey] = { intro: 90, outro: 120, enabled: true }`，纳入 `SYNC_KEYS` 与 `sync_state.py` 白名单，天然支持多设备云同步。
   - 交互设计：播放器设置项/控制栏新增「片头/片尾」，支持一键「设为片头起点（取当前 `currentTime`）」、「设置片尾提前跳过秒数（预设 60s / 90s / 120s）」；仅当某剧设置过且 `seekTime == 0`（新集）时生效，不干扰正常续播。
2. **第二阶段（可选增强）**：叠加 **方案 B**，在管理后台对热门剧集预设默认片头/片尾，客户端无个人设置时回退采用公共建议值。
3. **不建议阶段**：在平板 Termux 服务端跑 **方案 C**（`ffmpeg` 全量切片比对），算力与网络代价远高于收益。

### 4. 风险与边界
- 不同线路/清晰度偶尔存在几秒片源前贴片差异，需允许用户随时在播放中一键关闭或微调本剧设置。
- 片尾自动跳过只触发于「多集连续剧」且不能误在单集电影中启用。

## 任务 10：收藏更新提醒与推送通知（电视剧 + 书架小说）

### 1. 业务目标
- **电视剧收藏（`like`）**：当收藏的连载剧集新增集数或 `remark`（如“更新至第18集”）变化时提醒用户。
- **书架小说（`novel_shelf`）**：当书架中连载小说的最新章节数或最新章节标题变化时提醒用户。

### 2. 通知渠道方案对比

| 渠道 | 原理 | 优点 | 缺点 | 成本 |
|---|---|---|---|---|
| **A. 站内消息中心（红点 + 更新清单）** | 服务端定时巡检订阅并写入 `user_notifications` 表；前端打开 App / 切回前台时拉取未读角标与更新列表。 | 零第三方依赖、跨 Web 与 Android、零权限弹窗打扰 | App 彻底杀进程且未打开时不能弹窗 | **低（2 人日）** |
| **B. Android 原生轮询通知（WorkManager + Notification）** | Android 客户端在后台按每 2~4 小时周期唤醒拉取 `/api/notifications/unread`，有新内容时弹出系统通知栏提醒（点击直达详情/阅读）。 | 不依赖谷歌 FCM（国内小米平板可用）、离线可触达 | 受 MIUI 省电策略影响（需关闭电池优化，平板已常驻锁后台则稳定） | **中（2~3 人日）** |
| **C. 第三方推送 SDK（FCM / 极光 / 厂商通道）** | 接入第三方 SDK 与服务端推送密钥。 | 实时性最高 | 引入重依赖、国内网络 FCM 不可用、隐私与合规成本高 | **高（5+ 人日）** |

**推荐组合**：**A（站内通知中心） + B（Android 轻量 WorkManager 定时拉取发本地通知）**。既保证 Web/App 一致体验，又避开 FCM 在国内平板不可用的坑。

### 3. 核心机制设计

#### 3.1 数据模型（SQLite）
1. **收藏订阅快照表 `user_watch_items`**：
   - 字段：`(user_id, item_type ['vod'|'novel'], item_key, title, last_count, last_marker, notify_enabled DEFAULT 1, last_checked_at, updated_at)`
   - 说明：`user_sync` 保存同步数据时自动增量同步用户收藏的剧集与书架书籍到该表（并保留每部剧/每本书独立的 `notify_enabled` 开关）。
2. **站内通知表 `user_notifications`**：
   - 字段：`(id, user_id, item_type, item_key, title, message, delta_count, batch_key, read_at, created_at)`
   - 说明：`batch_key` 用于同一作品短时间内多集连更时的合并去重。

#### 3.2 更新判定逻辑
- **电视剧**：对 `notify_enabled = 1` 且处于未完结状态的剧集，由后端低频巡检（如每 2~4 小时分批巡检，复用 `catalog.py` 限流池）：调用 `detail()` 或轻量摘要接口比对 `episodes` 总数与 `remark`；若 `new_count > last_count`（或新最新集标题不同），判定为有更新。
- **小说**：对书架中 `notify_enabled = 1` 且非「已完结」的书籍，调用 `/api/reader/directory/detail` 获取最新章节总数 `len(chapters)` 与末章标题；若 `len(chapters) > last_count`，判定为更新了 `delta = new_count - last_count` 章。

#### 3.3 去重、合并与防打扰控制
- **单作品去重**：记录已通知的最大章节/集数水位线 `last_notified_count`，**绝不重复推送同一集/同一章**。
- **批量更新合并**：一次巡检发现连更 3 集或 5 章时，合并为一条通知：「《xxx》更新了 5 章，最新至第 128 章」；若 30 分钟内同一账号有多个作品同时更新，在 Android 本地通知栏合并为一条汇总通知。
- **限流保护**：后端巡检严格限速（每分钟最多探测 6~10 个去重作品；多用户收藏同一作品时**共享一次上游查询结果**），避免触发外部影视/小说上游风控封 IP。
- **用户开关**：
  - 全局开关：我的页面增加「收藏更新提醒」总开关；
  - 单作品开关：电视剧详情页「已收藏」旁 / 小说书架长按或详情页提供「接收更新提醒」开关（默认开启，可单独关闭某部剧或某本书）。

### 4. 实施成本与风险评估
- **总工作量**：后端表结构 + 去重调度 + 接口约 `2 人日`；前端通知中心 + 单作品开关约 `1.5 人日`；Android WorkManager 定时拉取与点击直达约 `1.5 人日`。**合计约 5 人日**。
- **主要风险**：
  1. 外部小说/影视上游接口限流风险 —— 通过「按作品去重共享查询 + 错峰分批巡检 + 完结作品停止巡检」控制；
  2. 多线影视换源导致集数命名差异 —— 以 `episodes.length` 增长为主要判定信号，辅以集名校验避免换源误报。
